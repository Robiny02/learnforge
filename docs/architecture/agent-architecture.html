LearnForge · Agent 架构orchestrator + tools

我们怎么「自己搭」了一个多 agent 系统 —— 以及到底拿什么替代了 LangGraph。

一句话结论：LangGraph 没被整个扔掉，但它被降级成一层很薄的线性外壳（START → plan → execute → aggregate → END，3 个节点直线连）。 真正的「agent 大脑」—— 路由、分支、重规划、ReAct 循环、唯一写者 —— 全部在 ManagerAgent 里用纯 Python 手搓。 换句话说：LangGraph 的条件边 DAG 被一个手写的 decide → dispatch → apply while 循环替代了，并且这个循环在没有 API key 时有完全确定性的兜底（“链路永远通”）。

1 · 两层：薄图壳 vs 手搓大脑

很多人以为「LangGraph 项目 = 用 LangGraph 的 StateGraph 画一张带条件边的状态机」。LearnForge 反过来：

典型 LangGraph 写法（我们没这么干）

  • 每个能力一个 node
  • add_conditional_edges() 把路由逻辑写进图的边
  • replan / 分支 = 更多节点 + 更多条件边
  • 状态靠 LangGraph 的 checkpointer 持久化
  • “下一步去哪”由图的拓扑决定

LearnForge 实际写法

  • 主图只有 3 个节点、直线连，没有一条条件边
  • 路由 / 分支 / replan 全在 manager_execute 这一个节点内部用 Python 循环跑完
  • “下一步去哪”由 ManagerAgent.decide_next() 决定，不由图决定
  • 状态放 SQLite（dialogue_turns / session_state），不靠图的 checkpointer
  • LangGraph 仅作 substrate（编译/调用入口）+ mock 子图的 interrupt/resume
orchestration/graph/main_graph.py — 整张主图就这么大
def build_main_graph() -> StateGraph:
    g = StateGraph(MainState)
    g.add_node(N.N_PLAN,      N.manager_plan)       # 只做记忆读取
    g.add_node(N.N_EXECUTE,   N.manager_execute)    # ← ReAct 循环全在这里
    g.add_node(N.N_AGGREGATE, N.manager_aggregate)  # 聚合成给用户的回复
    g.add_edge(START,        N.N_PLAN)
    g.add_edge(N.N_PLAN,     N.N_EXECUTE)    # 直线，没有 add_conditional_edges
    g.add_edge(N.N_EXECUTE,  N.N_AGGREGATE)
    g.add_edge(N.N_AGGREGATE, END)
    return g

→ 图本身不做任何决策。它只是「读记忆 → 干活 → 收尾」的三段壳。所有智能都被推进了中间那个节点。

2 · 编排者：agent-as-tool

架构范式是 orchestrator + tools：一个主 agent 规划并派发，每个域能力是它调用的一个工具（agent-as-tool）。

ManagerAgent （唯一编排者 + 唯一写者）
└─ 把每个能力当 tool 调用 ─┐
qa diagnose plan mock （+ 共享 retrieval）
工具角色内部子步骤（不是独立工具）
qa检索增强问答Router → Retrieval → Synthesizer → Verifier
diagnose只读弱点诊断ReAct 三段式（thought→action→observation）
plan生成/修改学习路径只产增量 PathDiff，由 Manager 落库
mock多轮模拟面试Interviewer / Judge / Strategist / Coach
命名纪律：这不是「13-agent 系统」。Router / Synthesizer / Judge / Coach 是工具内部的子步骤，对外只有上面 4 个工具。 关键不变量：Manager 是唯一写者 —— 只有它写 knowledge_atoms 掌握度和 learning_paths；DiagnosisAgent 严格只读（有测试守护）。

3 · 替代 LangGraph 的核心：手搓 ReAct 循环

这是整篇文档的重点。LangGraph 用条件边在节点间跳转来实现「看结果决定下一步」；LearnForge 把这件事换成了 ManagerAgent.execute_dynamic() 里一个朴素的 for 循环。Manager 不预先拆死一张 DAG，而是每一步看子 agent 的结果，再决定下一步。

┌──────────── for _ in range(max_steps) ────────────┐
│ decide_next() → dispatch(agent) → _apply_step() │
│ 选下一个子 agent    派给域 worker    善后/唯一写者落库 │
└────────── 直到 next == "finish" / 预算用尽 ─────────┘
orchestration/manager.py — execute_dynamic()（精简）
done, responses = [], []
for _ in range(max_steps):
    nxt = self.decide_next(user_input, done, responses, context)
    if nxt == "finish": break
    if nxt in done:  break            # 防止反复调同一个 agent 死循环

    # §5.6 异常①：要改计划但诊断为空 → 跳过，改建议先 mock
    if nxt == "planning" and _is_empty_diagnosis(context.get("diagnosis", {})):
        meta["suggest_mock"] = True; done.append("planning"); continue

    resp = self.dispatch(nxt, user_input, context, trace_id)  # 派给 worker
    self._apply_step(nxt, resp, context, meta, trace_id)     # 唯一写者在此落库
    done.append(nxt); responses.append(resp)

    # 早停：qa 是叶子能力，答完即终态，省一次 decide_next 往返
    if nxt == "qa" and resp.status == Status.OK: break
这就是「自己搭 agent」最实在的含义：编排逻辑是普通 Python 控制流（for / if / break / continue）， 而不是一张需要你脑补拓扑的图。复合任务「诊断 → 改路径 → 建议 mock」是这个循环自然续跑出来的，没有为它单独连边。

4 · decide_next：LLM 选下一步 + 确定性兜底

循环每一步的「下一步去哪」由 decide_next() 回答。它把受限动作空间{qa, planning, diagnosis, mock, finish} 喂给一个便宜模型， 让它只输出一个 2 字段的 NextStep。关键设计：

  • 动作空间受限且安全：模型只能从 5 个里选一个，选错/解析失败一律落到确定性兜底。
  • 喂「为什么」而不只是结论：把每个子工具的 reason（依据/缺口/降级，如「diagnosis 信号不足」「qa 降级无证据」）一起喂给 replan，让它看到结论背后的理由。
  • 护栏防过早 finish：弱模型常在 diagnosis 后就想收尾；如果用户明确要学习计划，planning 跑之前不允许 finish。
  • 无 LLM 时完全确定性：LLM.available == False → 走 _fallback_next()，用关键词先验复刻「看结果选下一步」的直觉。这就是「链路永远通」——所有测试可离线跑。

在线（有 key）

  • LLM 输出 NextStep.next_agent
  • 非法值 → 落兜底
  • 首步不允许直接 finish（防空转）
  • 护栏拦「计划没跑就 finish」

离线（无 key）

  • _fallback_next() 关键词路由
  • 复合「准备面试」：diagnosis → planning → finish
  • 单意图：首步按关键词，完成即 finish
  • 确定、可回归、零成本

5 · 两种编排模式

Manager 按意图分两条编排路径，写入口统一收口在 dispatch / _apply_step（唯一写者不变）：

模式触发怎么走
动态 ReAct
execute_dynamic		 单意图（问个概念、单独诊断…） 每步 decide_next 实时选下一个 agent，看结果再决定。叶子能力（qa）答完即停。
plan-as-tool-calls
planner.build_plan		 复合意图（“快面试了帮我准备一下”） 先 create 一个显式、可检视、可标记的有序步骤计划（每步选一个子 agent），执行器逐步 dispatch + mark_step=completed。已知复合用确定性拆解，可回归。

两种模式都不依赖 LangGraph 的边 —— 一个是 Python 循环，一个是 Python 遍历一个 plan 对象。LangGraph 自始至终只负责把这一切包在 manager_execute 节点里调用一次。

6 · 工具层：BaseAgent + Skill 权限门

每个工具继承 BaseAgent，并从 SkillRegistry 取自己的 Skill（运行时人格）。这让每个子 agent 更像 Claude Code 的 subagent：职责、上下文、可用工具都由 skill 声明，而非外层 workflow 默许。

每个工具 = 三层，刻意分开：

层是什么在哪
契约Input/Output Pydantic = 工具 schemacontracts/agents/<tool>.py
运行时人格system_prompt + 工具权限 + model_tierskills/definitions/__init__.py
工程文档职责/不变量/降级/坑各目录 CLAUDE.md（≠ system prompt）
agents/base.py — 运行期权限门禁（require_tool）
def require_tool(self, tool_name):
    # subagent 未被 skill 授权 → 直接阻断，不靠外层默许
    if not self.has_tool(tool_name):
        raise SkillPermissionError(
            f"Agent '{self.agent_id}' skill is not allowed to use '{tool_name}'.")

写工具不会出现在只读 agent 的工具表里 —— 这就是 DiagnosisAgent「严格只读」在运行期被强制的方式。

7 · 真·tool-calling ReAct（react/loop.py）

除了 Manager 那层「选哪个子 agent」的编排循环，工具内部还有一个真正的 OpenAI 兼容 tool-calling 循环 ReactRunner：维护对话 messages → 模型吐 tool_calls → 逐个过权限门 + 执行 → 结果作为 role=tool 回灌 → 再问模型，直到它不再调工具就给最终答案。

think→tool_call→observe (role=tool 回灌)↺无 tool_calls → 最终文本
  • 只暴露 skill.allows(name) ∧ 有 handler 的工具，越权 → error tool_result（不崩溃）。
  • 没有 tool_calls 时直接返回 → 这就是「简单问题快答」路径（模型不调工具直接答）。
  • 超 max_steps → 再要一次「基于已观察直接给最终答复」，安全收尾并标 degraded。

注意区分两个「ReAct」：Manager 的 ReAct 是「选下一个子 agent」的编排循环；ReactRunner 是「在一个工具内反复调 MCP 工具」的执行循环。diagnose 用前者的三段式直觉，未来的 research 工具用后者。

8 · 固定 8 层 Prompt Stack

所有子 agent 的每一次 LLM 调用都走同一套有序、分层、KV-cache 友好的 prompt 装配（memory/context_assembler.assemble_prompt）。前 5 层对同一 agent 稳定 → 当可缓存 prefix；后 3 层每轮变 → volatile 尾部。

稳定 prefix（可缓存）
1System / Constitution身份 + 安全 + 格式不变量
2Project Guide项目级运行时约束（PROJECT_GUIDE.md）
3User Memory用户长期稳定偏好（MEMORY.md）
4Active Skill当前 agent 的 SOP / persona（怎么做事）
5Tool Registry能用什么工具 + 边界 + 输出 schema
易变尾部（每轮变）
6Conversation State最近发生了什么 / 有哪些 artifact 可引用
7Evidence这轮回答基于的具体材料（检索/附件/工具结果）
8User Input当前用户输入

冲突解决：越靠后优先级越高，但安全/格式不可被 User Input 覆盖，Evidence 优先于模型先验。这套分层是「自己搭 agent」里相当于框架替你做的那部分 —— 我们手写了它，因此能逐层报 token、控制缓存边界。

9 · 状态不放在图里，放在 SQLite

典型 LangGraph 用 checkpointer 持久化图状态。LearnForge 把对话状态收口到 SQLite，图基本无状态：

  • dialogue_turns —— 会话账本（role / capability / route_mode / topic / tool_calls / artifacts），路由的 last_capability 由它重算（带 aside 衰减）。
  • session_state —— 短期会话记忆：pinned（重要结果永不压缩）+ 早期压缩 summary + 最近原文轮。
  • 会话级 compaction（Claude Code 风格）：按 token 阈值而非轮数折叠最旧轮进 summary，至少保留 N 轮；周期性全量重摘修正漂移。详见 record_turn()。

好处：无状态 HTTP 下每轮从 SQLite 重建上下文；不依赖某个进程内的图实例存活；NEEDS_INPUT 追问回路天然支持（这轮返回问题，下轮带答案回来）。

10 · LangGraph 还剩什么 & 为什么这么搭

LangGraph 仍然保留的地方

  • 主图外壳：3 节点直线，作为统一的 compile/invoke substrate（main_graph.py）。
  • mock 子图：S1–S7 状态机，真正用到 LangGraph 的 interrupt() / Command(resume=...) 做多轮人机交互（S3 等用户答题、S_PAUSE）。这是 LangGraph 最不可替代、留它最值的地方。

为什么把大脑手搓出来，而不是交给图

诉求手搓循环怎么满足
离线确定性（“链路永远通”）每个 LLM 决策点都有确定性兜底；无 key 时整条编排是纯规则、可回归。
安全 / 受限动作空间下一步只能从 {qa,planning,diagnosis,mock,finish} 里选，非法即落兜底 —— 比开放的图跳转更可控。
唯一写者不变量所有写都收口在 _apply_step；图不直接写状态，工具只产增量。
可观测 / 可解释普通 Python 控制流，断点即真相；executed 列表直接画出链路给 UI/trace。
喂「为什么」做 replan把子工具的 reason（依据/缺口/降级）显式喂回 decide_next —— 这种细粒度反馈在边-条件式 DAG 里很别扭。
所以「用什么替代了 LangGraph」？
答案是：一个手写的、动作空间受限的 ReAct 编排循环（ManagerAgent.execute_dynamic / decide_next / _apply_step）， 配上显式 plan-as-tool-calls、Skill 权限门、固定 8 层 Prompt Stack 和 SQLite 状态。 LangGraph 从「状态机框架」退化为「一层调用壳 + mock 的 interrupt/resume 引擎」。智能不在图里，在 Python 里。
